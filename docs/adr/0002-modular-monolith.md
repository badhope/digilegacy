# ADR-0002：M0-M2 采用模块化单体，不拆微服务

- 状态：Accepted
- 日期：2026-11-19
- 决策人：架构负责人
- 相关：G18、性能与部署

## 背景

项目处于重建期，真实负载、热点、数据边界都还没有稳定。过早拆微服务会引入网关、服务发现、分布式事务、跨服务审计和部署复杂度，但没有对应的收益。

## 决策

M0-M2 采用单进程模块化单体：

- `core/` 按领域拆 crate，依赖方向固定。
- `apps/` 是入口，不是业务层。
- 所有入口走同一个 `CommandBus`。
- 先保证模块边界、契约、测试与性能预算。
- 只有出现明确的独立伸缩/隔离/团队边界需求时才拆服务。

## 替代方案

- 一开始就拆 assets/plan/deliver/agent 服务：部署与调试成本过高。
- 单体但无模块边界：会退化成大泥球。
- 直接上事件总线：当前没有跨服务事件需求。

## 后果

好的方面：

- 本地可一键启动，调试链路短。
- 事务与审计在一个进程内更容易保证。
- 可以先验证真实热点，再决定拆分。

代价：

- 单进程故障域较大，需要靠模块隔离与测试补偿。
- 后续拆分需要提前设计命令边界和幂等性。
- 数据库连接与长任务需要单独的隔离策略。

## 复审条件

- 单一领域需要独立伸缩或独立发布。
- 单进程内存/CPU 成为可测量的瓶颈。
- 多团队并行导致 crate 边界无法维持。
