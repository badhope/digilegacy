# ADR-0001：契约先行，生成物不手改

- 状态：Accepted
- 日期：2026-11-19
- 决策人：架构负责人
- 相关：G06、G15、G16、G18

## 背景

Web、CLI、HTTP、MCP、mock 各自维护一套命令名、字段、错误码，会迅速漂移：前端能调的命令 CLI 没有、MCP 暴露了写工具、OpenAPI 与实现不一致。旧版应用已经出现过命令/页面/文档事实不一致的维护成本。

## 决策

以 `contracts/commands.json`、`tools.json`、`errors.json`、`schemas/`、`mocks.json` 为唯一事实源。所有消费者由 `tools/generate.mjs` 派生，生成文件不手改。

约束：

- 命令必须有 input/output schema。
- 工具只能引用已有命令。
- 写工具必须 `approval=required`。
- MCP 只能暴露 `read`/`draft`。
- HTTP 传输必须是 `METHOD /api/v1/...`。
- `--check` 失败即阻断合并。

## 替代方案

- 手写多份类型：短期快，长期必漂移。
- 只用 OpenAPI 作为源：无法覆盖 CLI/MCP 的审批与工具语义。
- 每个入口维护自己的 schema：直接否决。

## 后果

好的方面：

- 新增命令的消费者成本低。
- 权限与审批可以在生成阶段强制。
- 测试可以针对 manifest 做一致性检查。

代价：

- 生成器本身成为关键基础设施，需要测试与版本管理。
- 生成代码可读性差，必须通过文档和 `--check` 补偿。
- 复杂业务字段仍需要在领域层建模，不能只靠 JSON Schema。

## 复审条件

- 生成器需要支持超过 3 种不兼容的传输语义。
- 生成物出现无法用模板表达的领域行为。
- 契约规模导致生成/检查超过 10 秒。
