# 07 · 平台化前端与前后端映射

> 本文件纠正上一版的定位错误：**产品本体是平台，不是桌面应用；前端是平台控制台，Agent 工具是一等公民。**
> 本文件与 `03` 的关系：`03` 保留页面级交互细节；入口结构、Agent 工作台、前后端映射以本文件为准。
> 加载顺序、模块边界、工程治理分别见 `08 §2`、`08 §3`、`08 §4`。

## 1. 定位纠正

### 1.1 上一版错在哪

| 错误 | 表现 | 后果 |
|---|---|---|
| 把桌面壳当产品本体 | 架构写“单机应用”“Windows 桌面”，前端按 Tauri 窗口设计 | 平台能力被降级成“本地工具” |
| 前端=页面集合 | 10 条旧路由、5 个分组、15 张卡堆在 ProfileView | 使用逻辑按“功能”而非“对象/任务”组织 |
| Agent=侧边聊天 | 助手只是抽屉，ReportView 里还塞了 Agent 卡和 AI 对话 | Agent 无法驱动平台，只是问答装饰 |
| 后端=IPC 命令 | 前端只认 `invoke`，HTTP/CLI/MCP 是附属 | 无法做平台 API、外部 Agent、第三方集成 |
| 设置=一个页面 | 安全/备份/连接/外观全塞 ProfileView | 同一概念多处出现，重复且难维护 |

### 1.2 新定位

**一句话：** 一个 API-first 的数字遗产平台——人用控制台，Agent 用工具，双方操作同一套平台能力。

```text
┌─────────────────────────────────────────────────────────────┐
│ 客户端：Web 控制台（主） / 桌面壳（可选） / CLI / MCP / 第三方 │
└───────────────────────────┬─────────────────────────────────┘
                            │ Platform API（REST + SSE，版本化，统一鉴权）
┌───────────────────────────▼─────────────────────────────────┐
│ Agent 层：Agent Runtime / Tool Registry / Approval / Run Log │
└───────────────────────────┬─────────────────────────────────┘
                            │ 同一套命令总线（权限、校验、信封、审计）
┌───────────────────────────▼─────────────────────────────────┐
│ 平台核心：资产 / 规划 / 政策 / 交付 / 审核 / 触发 / 安全 / 存储 │
└─────────────────────────────────────────────────────────────┘
```

**四条硬规则：**

1. **Web 控制台是主客户端。** 桌面壳只是同一套控制台的打包方式，不承载业务逻辑；本地不是卖点。
2. **Agent 不是聊天窗口，是平台驱动器。** Agent 通过 Tool Registry 调用平台命令，不模拟鼠标、不点 DOM、不维护第二套后端。
3. **人和 Agent 同权限、同审计、同审批。** Agent 能做的事，人也能做；Agent 不能绕过人不能绕过的限制。
4. **一个能力只有一个后端实现。** 页面、Agent、CLI、MCP 全部走同一个 CommandBus / 领域服务。

**本期平台形态：** 单工作区、可自托管/私有部署；保留 `workspaces` 表与 workspace 抽象；多租户、成员体系、计费不在一期，后续加 `workspace_id` 列即可扩展。

### 1.3 平台边界

| 层 | 负责 | 不负责 |
|---|---|---|
| 平台核心 | 领域规则、数据、安全、渲染、审计 | 页面布局、Agent 话术 |
| Platform API | 资源路由、鉴权、分页、SSE、版本 | 业务规则（下沉到领域服务） |
| Tool Registry | 工具清单、权限、审批策略、调用审计 | 另写一套业务逻辑 |
| Agent Runtime | 计划、工具循环、取消、预算、运行记录 | 直接改库、直接发邮件 |
| Web 控制台 | 展示、交互、状态、无障碍 | 直接访问 SQLite/文件系统 |
| 桌面壳 | 窗口、托盘、单实例、更新 | 业务逻辑、独立数据路径 |

## 2. 前端信息架构

### 2.1 5 个主入口 + 设置工具区

| # | 入口 | 回答的问题 | 核心对象 |
|---|---|---|---|
| 1 | **概览 Overview** | 平台现在什么状态、我该做什么、有哪些待批准 | 运行态、待办、审批、风险 |
| 2 | **资产 Assets** | 我有哪些账号、每项怎么处置 | Asset、Platform、Discovery |
| 3 | **规划 Planning** | 我失联后谁来接、怎么接 | Profile、Heir、Trigger、CheckIn |
| 4 | **交付 Deliverables** | 家人拿到什么、能不能照着做 | Report、Guide、Legal、Toolkit、Review、Drill |
| 5 | **自动化 Automation** | Agent 能做什么、做过什么、哪些要我批 | Agent、Tool、Run、Approval、Schedule |

**设置（Settings）不占主导航**，放在右上角账户/齿轮工具区。理由：设置是全局工具，不是业务旅程的一站；而 Agent 是平台一等公民，必须有独立工作台。

> 这仍然满足“5 个主入口”，但第 5 个从“设置”换成“自动化”。这是平台定位的直接结果，不是多加一个页面。

### 2.2 全局框架

```text
┌──────────────────────────────────────────────────────────────────┐
│ 顶栏：Workspace 名 · 全局搜索(⌘K) · 通知 · Agent 状态 · 账户/设置 │
├──────────┬───────────────────────────────────────────────────────┤
│ 概览     │ 页面内容                                               │
│ 资产     │                                                       │
│ 规划     │                                                       │
│ 交付     │                                                       │
│ 自动化   │                                                       │
└──────────┴───────────────────────────────────────────────────────┘
                                     右侧：全局 Agent 抽屉（⌘J）
```

- 侧栏 5 项固定，不出现二级导航；页面内用标签/分段控制。
- 顶栏 Agent 状态显示：空闲 / 运行中 / 等待批准 / 失败；点击进 Automation。
- 全局 Agent 抽屉只做“快速问答 + 当前任务跟踪”，长任务自动跳到 Automation 的 Run 详情。
- 设置入口在账户菜单：工作区 / 安全 / 数据 / 连接 / 外观 / 审计 / 关于。

| 路由 | 页面 | 说明 |
|---|---|---|
| `/overview` | 概览 | 平台运行态、待办、审批、风险 |

### 2.4 页面职责边界

| 页面 | 只负责 | 明确不负责 |
|---|---|---|
| 概览 | 聚合状态、生成待办、展示待审批 | 编辑任何实体、生成报告 |
| 资产 | 资产 CRUD、发现、筛选、批量归档/导出 | 继承人管理、触发配置、报告模板 |
| 规划 | 持有人、继承人、执行人、触发、签到 | 资产明细编辑、法律文书渲染 |
| 交付 | 生成/预览/导出/审核/演练 | 修改资产数据（只读快照） |
| 自动化 | Agent/工具/运行/审批/计划任务 | 业务数据编辑（通过工具调用） |
| 设置 | 工作区、连接、安全、数据、外观、审计 | 业务对象 CRUD |

## 3. 使用逻辑

### 3.1 人的主路径

```text
首次：创建工作区 → 设置主密码 → 发现/登记资产 → 指定继承人 → 配置触发 → 生成交付物 → 演练
日常：概览待办 → 点进对象 → 做一个动作 → 回概览（待办自动减少）
交付：交付页 → 选类型 → 预览 → 质量审核 → 导出 → 记录哈希
```

**三个“不绕路”原则：**

1. **待办即入口。** 概览的每个待办都带深链，点进去就是修复位置，不让用户自己找页面。
2. **对象即页面。** 资产、继承人、交付物、Agent Run 各有唯一详情页；其他页面只引用，不复制一份编辑界面。
3. **动作即命令。** 每个按钮对应一个命令名；按钮 disabled 时说明原因（锁定/无权限/缺前置）。

### 3.2 Agent 的驱动路径

```text
用户在对象上点“交给 Agent”
  → 创建 AgentRun（绑定对象与目标）
  → Agent 规划步骤（只读工具自动执行）
  → 需要写操作时生成 Approval（展示 diff / 影响范围）
  → 用户批准/拒绝/修改
  → 批准后执行同一命令
  → SSE 推送 run/对象变更
  → 页面缓存失效，详情页显示新值
  → Run 详情保留完整时间线与审计
```

**一个具体例子：** 用户说“帮我找出没指定继承人的资产，并生成缺口清单”。

```text
assets.list(read) → heirs.list(read) → 计算缺口(draft)
→ deliverables.generate(draft 缺口清单，不落最终态)
→ 若用户要把缺口补进规划：plan.update(write) 生成 Approval（diff=哪个资产/哪个继承人）
→ 批准后落库 → entity.changed → 概览待办减少
```

这个例子里，Agent 没有碰数据库、没有点页面，只调用平台工具；写操作被人批准后才生效。

**Agent 的三种入口：**

| 入口 | 用途 | 生命周期 |
|---|---|---|
| 对象级“交给 Agent” | 针对一个资产/一份报告做具体事 | 绑定对象，产出建议或修改 |
| 全局 Agent 抽屉（⌘J） | 快速问答、跨对象查询、发起任务 | 短会话；长任务跳 Automation |
| Automation 工作台 | 管理 Agent、工具、运行、审批、计划任务 | 平台级，可审计、可取消、可复跑 |

**Agent 不能做的事：**

- 不能直接改数据库、文件、密钥；
- 不能自动批准自己的写操作；
- 不能调用 `key` / `network` / `desktop` 工具；
- 不能隐藏工具调用与失败；
- 不能把用户数据发到未配置的端点。

### 3.3 操作员路径

平台管理员/高级用户：

```text
Automation → 工具目录 → 查看权限与审批策略
Automation → Agent → 启停、模型、预算、可用工具
Automation → 运行 → 查看步骤/耗时/成本/失败
Automation → 审批 → 批量批准/拒绝（带 diff）
Automation → 计划任务 → 政策同步、完整度检查、备份提醒
设置 → 审计 → 导出审计链
```

### 3.4 状态与权限

| 状态 | UI 表现 | 可操作 |
|---|---|---|
| 未初始化 | 引导创建工作区/主密码 | 仅引导 |
| 锁定 | 全局遮罩，敏感字段显示“需解锁” | 解锁/恢复 |
| 只读（外部访问） | 顶栏“只读会话” | 读、导出（若允许） |
| 降级（连接失败） | 页面内警告 + 重试 | 本地功能可用，相关能力禁用 |
| Agent 运行中 | 顶栏状态 + 对象页进度条 | 查看、取消、转人工 |
| 等待批准 | 审批徽标 + diff 预览 | 批准/拒绝/修改 |
| 失败 | 错误码 + traceId + 重试 | 重试/导出诊断 |

**权限矩阵：**

| 角色 | 读 | 写 | 密钥/网络 | Agent 管理 | 审批 |
|---|---|---|---|---|---|
| 持有人（本机） | 是 | 是 | 是 | 是 | 是 |
| 家人/执行人（只读） | 是 | 否 | 否 | 否 | 否 |
| 外部 Agent | 是（工具白名单） | 需审批 | 否 | 否 | 否 |
| 平台管理员 | 是 | 是 | 是 | 是 | 是 |

## 4. 前后端对应

### 4.1 一条主链路，两个调用者

```text
Web 控制台 ──► platformClient（生成） ──► Platform API ──► CommandBus ──► 领域服务 ──► Store
Agent ──────► Tool Registry ───────────► CommandBus ──► 同一领域服务 ──► Store
CLI/MCP ────► Platform API / Tool API ──► CommandBus ──► 同一领域服务 ──► Store
```

**禁止：**

- 页面直接 `invoke` 某个后端函数（必须走生成客户端）；
- Agent 直接写库/发邮件/读文件；
- 为 Agent 单独写一套业务逻辑；
- 前端自己拼 SQL/路径/密钥。

### 4.2 页面 → API → 命令 → 工具 映射

| 页面 | 读取 | 写入/动作 | 命令 | Agent 工具 | 主要表 |
|---|---|---|---|---|---|
| 概览 | `GET /api/v1/overview`、`GET /api/v1/audit/events`、`GET /api/v1/agent/runs?status=active` | 无（只跳转） | `app.overview`、`audit.list`、`agent.runs.list` | `overview.get`、`audit.list`、`agent.runs.list` | assets、plan、audit_log、agent_run_log |
| 资产 | `GET /api/v1/assets`、`GET /api/v1/assets/:id`、`GET /api/v1/platforms` | 创建/编辑/归档/导入/发现 | `assets.list/get/create/update/archive`、`discovery.recommend/apply` | `assets.list/get/create/update/archive`、`discovery.recommend/apply` | digital_assets、platforms |
| 规划 | `GET /api/v1/plan`、`GET /api/v1/heirs`、`GET /api/v1/triggers`、`GET /api/v1/checkins` | 保存档案/继承人/触发/签到/暂停 | `plan.get/update`、`heirs.*`、`triggers.*`、`trigger.checkin/pause` | `plan.get/update`、`heirs.*`、`triggers.*`（写需审批） | user_profile、heirs、dms_config、check_in_log |
| 交付 | `GET /api/v1/deliverables`、`GET /api/v1/deliverables/:id`、`GET /api/v1/reviews`、`GET /api/v1/drills`、`GET /api/v1/jobs/:id` | 生成/预览/导出/审核/演练 | `deliverables.list/generate/export`、`reviews.*`、`drills.*` | `deliverables.list/generate/export`、`reviews.list/decide`（人工）、`drills.start/complete` | deliverable_exports、jobs、review_records、drill_runs |
| 自动化 | `GET /api/v1/agent/runs`、`GET /api/v1/agent/approvals`、`POST /api/v1/agent/plan` | 启停 Agent/工具、取消运行、批准/拒绝 | `agents.*`、`tools.list`、`agent.runs.*`、`approvals.decide` | **仅元工具**：`tools.list`、`runs.get`；`approvals.decide` 禁止 Agent 调用 | connections、agent_run_log、audit_log |
| 设置 | `GET /api/v1/workspace`、`GET /api/v1/connections`、`GET /api/v1/security`、`GET /api/v1/audit` | 保存连接/改密/备份/诊断 | `workspace.*`、`connections.*`、`security.*`、`backup.*`、`diagnostics.export` | 仅 `connections.list/status`；密钥/网络工具禁止 | connections、security_config、audit_log |

> 工具名与命令名同名是默认；需要不同语义时在 `contracts/tools.json` 显式映射，不允许前端/Agent 各记一套。

### 4.3 前端数据规则

| 规则 | 做法 |
|---|---|
| 服务端状态唯一 | TanStack Query（或等价 query 层）管缓存；Pinia 只存 UI 状态（侧栏、抽屉、主题） |
| 缓存键 | `['assets', filters]`、`['asset', id]`、`['run', id]`；不把整页状态塞进一个 store |
| 失效 | SSE `entity.changed` / `run.updated` 触发精确失效；写命令成功后主动失效对应键 |
| 分页 | 游标分页；列表不一次性拉 1000 条；虚拟列表 |
| 写操作 | 服务端 ack 后再改缓存；仅本地草稿可乐观更新 |
| 错误 | 统一信封 → `ErrorState`；401/403/423 分别进登录/无权限/锁定态 |
| 锁定 | 全局 `security.status`；敏感组件订阅锁定态，不自行判断 |
| 权限 | `me.permissions` 控制可见/禁用；服务端仍二次校验 |
| 实时 | `GET /api/v1/events` SSE；断线指数退避，恢复后全量刷新关键查询 |
| 幂等 | 创建类命令带 `Idempotency-Key`；重复点击不产生重复资产/导出 |
| 加载 | 启动顺序、骨架、预取、长任务进度见 `08 §2`；首屏只等最小数据 |

### 4.4 契约生成

```text
contracts/commands.json ──► CommandBus 注册 / CLI / HTTP 路由 / MCP 工具 / mock
contracts/errors.json   ──► Rust 错误 / TS 类型 / 文案键 / CLI 退出码
contracts/openapi.json  ──► TS platformClient（类型 + 方法 + 错误）
contracts/tools.json    ──► Agent Tool Registry（JSON Schema + 权限 + 审批）
contracts/schemas/*.json──► 运行时校验（前后端同一份）
```

规则：

- 前端不得手写 URL/命令字符串；全部从生成客户端取。
- `contracts:check` 校验七方集合差集；手改生成物 CI 直接红。
- OpenAPI 与 commands 双向校验：每个资源路由必须对应命令，每个命令必须有传输映射。
- Agent 工具只能引用命令，不新增业务语义。

### 4.5 桌面壳、CLI、MCP 的定位

| 客户端 | 怎么接 | 不做什么 |
|---|---|---|
| Web 控制台 | Platform API | 不碰本地文件/SQLite |
| 桌面壳 | 加载同一套 Web 控制台；可内嵌本地核心或连远程 API | 不写业务逻辑、不做第二套页面 |
| CLI | Platform API / 本地核心 | 不绕过权限与审计 |
| MCP | Tool Registry 的只读/草稿工具 | 不暴露 key/network/desktop |
| 第三方 | Platform API + OAuth/token | 不直连数据库 |

### 5.4 去重规则（写死）

1. **一个实体一个详情页。** 资产、交付物、Run 不在列表页内展开完整编辑。
2. **一个概念一个组件。** 资产卡、状态徽标、空态、错误态、审批卡全局复用，不允许页面各写一套。
3. **一个动作一个命令。** 按钮必须能说出命令名；同一动作不在两个页面出现。
4. **概览不复制详情。** 概览只放状态、待办、审批、风险；不放完整表格。
5. **设置不散落。** 安全/备份/连接/外观只在 Settings；业务页面最多给深链。
6. **业务页不放 AI 对话。** 对话只在全局抽屉/Automation；页面只放“交给 Agent”动作。
7. **内容审核 ≠ Agent 审批。** 前者在 Deliverables/质量，后者在 Automation/审批，不能合成一个队列。
8. **导出只有一个入口。** 统一在 Deliverables；资产页只允许“导出资产 JSON”，不重复报告导出。
9. **签到只有一个入口。** 顶栏全局签到 + Planning/触发详情；不在 Dashboard/DMS 各放一个。
10. **发现不是页面。** 发现是 Assets 的向导动作，不占导航。

## 6. Agent 工具契约

### 6.1 Tool Manifest

```json
{
  "name": "assets.update",
  "title": "更新资产",
  "description": "修改一个已有资产的字段，返回更新后的资产",
  "permission": "write",
  "approval": "required",
  "input_schema": "schemas/assets.update.input.json",
  "output_schema": "schemas/assets.update.output.json",
  "idempotent": false,
  "audit": true,
  "human_equivalent": "assets.update",
  "available_to": ["builtin", "external"],
  "rate_limit": "30/min",
  "bulk_threshold": 10
}
```

### 6.2 权限与审批矩阵

| 工具类型 | 例子 | Agent 可调用 | 审批 |
|---|---|---|---|
| `read` | `assets.list`、`deliverables.get` | 是 | 不需要 |
| `draft` | `deliverables.generate`（草稿）、`reviews.suggest` | 是 | 不需要（不落最终态） |
| `write` | `assets.update`、`plan.update` | 是 | **默认需要** |
| `write` 批量 | 批量归档 >10 条 | 是 | **必须**，展示条数与影响 |
| `key` | 改密、恢复、库密钥 | 否 | — |
| `network` | 测试连接、政策拉取、发邮件 | 否 | 仅人类在 Settings 触发 |
| `desktop` | 托盘/自启/窗口 | 否 | — |

### 6.3 事件（SSE）

```json
{ "type": "run.step", "runId": "run_...", "step": 2, "title": "检查资产完整性" }
{ "type": "tool.called", "runId": "run_...", "tool": "assets.list", "permission": "read" }
{ "type": "approval.requested", "runId": "run_...", "approvalId": "apr_...", "summary": "将修改 3 个资产", "diff": "..." }
{ "type": "run.completed", "runId": "run_...", "status": "succeeded", "tokens": 1200, "cost": 0.03 }
{ "type": "job.updated", "jobId": "job_...", "kind": "export", "status": "running", "progress": 0.6 }
```

规则：

- 事件只带摘要与引用，不推凭据/明文；
- 断线重连带 `Last-Event-ID`，服务端补发；
- 前端收到 `entity.changed` 后按实体键失效，不整页刷新。

### 6.4 UI 行为

- 抽屉里出现写操作 → 显示“等待批准”，不显示“已完成”；
- 审批卡展示：工具、对象、diff、影响条数、可回滚点；
- 批准后按钮变“已执行”，并给对象详情深链；
- 拒绝必须填理由（写审计）；
- 失败显示错误码 + traceId + “转人工”。

### 6.5 反模式

- Agent 模拟鼠标/键盘操作 UI；
- Agent 直接调用内部函数绕过 CommandBus；
- Agent 写操作自动批准；
- Agent 调用 `key`/`network`/`desktop`；
- 前端为 Agent 单独开一套接口；
- 运行记录只存成功，不存失败与审批。

## 7. 前端工程结构

```text
web/src/
  app/            入口、路由、全局布局、providers
  features/
    overview/
    assets/
    planning/
    deliverables/
    automation/
    settings/
  entities/       资产/继承人/交付物/Run 的模型、卡片、状态
  shared/         ui、表单、表格、空态、错误、diff、时间线
  platform/       platformClient、SSE、权限、锁定、i18n
  design/         tokens、主题、动效
```

规则：

- `features` 不直接 import 另一个 `features`；跨页复用下沉到 `entities/shared`。
- 页面只做编排：取数 → 组件 → 命令；业务规则在后端。
- 每个 feature 有 `api.ts`（只用生成客户端）、`queries.ts`、`components/`、`routes.ts`。
- `features` 之间禁止互相 import；跨页复用下沉到 `entities/shared`；边界由 `08 §3.4` 架构测试阻断。
- 路由懒加载；首屏只加载 Overview 所需 chunk。
- 错误边界按 feature 隔离，单页失败不白屏。
- 主题/语言/密度走设计令牌；不写页面级硬编码颜色。
