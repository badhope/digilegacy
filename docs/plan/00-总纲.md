# 00 · 项目总纲

## 1. 产品定义

**一句话：** 一个 API-first 的数字遗产平台：人用控制台，Agent 用工具，双方操作同一套平台能力。

**三句展开：**
1. 平台核心管理资产、继承人、处置决定、触发链、审核与交付物。
2. Web 控制台让人完成盘点、规划、交付、演练；桌面壳只是可选打包。
3. Agent 通过工具注册表驱动平台：只读自动、写操作审批、全程审计。

**不成立的定位：** “本地优先”“无云”“无遥测”不再作为卖点；它们只是数据存放与隐私说明，不写在首屏。把产品说成“桌面工具”同样不成立。

## 2. 用户与任务

| 角色 | 核心任务 | 成功的样子 |
|---|---|---|
| 持有人（主用户） | 盘点、决定、指定、触发 | 30 分钟内完成一份可交付的规划 |
| 继承人/执行人 | 在无人讲解时照清单办理 | 打开工具包就知道第一步做什么 |
| 平台管理员/高级用户 | 管 Agent、工具、连接、审计 | 能看清每次运行与每次写操作 |
| Agent / 集成方 | 通过工具完成批量核对、起草、检查 | 工具可发现、权限明确、结果可审计 |
| 技术型用户 | 接自己的模型/数据源、脚本化核对 | CLI 与 API 能完成同样的事 |

**唯一验收基准：** 家人拿到东西后，能不能在没有任何人帮助的情况下走完全程。

**平台验收基准：** Agent 只通过工具、在权限内完成一次真实任务（读 → 草案 → 审批 → 落库），全程可审计；页面与 Agent 看到的是同一份数据。

## 3. 范围

### 3.1 本期做

- 平台核心：资产发现 → 分类登记 → 处置规划 → 文档交付 → 到期触发 → 家人执行的六段闭环。
- Web 控制台（主客户端）：5 个主入口（概览/资产/规划/交付/自动化）+ 全局 Agent 抽屉。
- Agent 工具层：Tool Registry、运行记录、写操作审批、取消、预算、审计。
- 客户端：Web 控制台、桌面壳（可选）、CLI、HTTP Platform API、MCP。
- LLM 接入（OpenAI 兼容：助手、流式、Agent 工具循环、审核预审）。
- 平台政策数据 API：拉取 → diff → 候选 → 人工批准 → 落库。
- 安全内核：字段加密、两层密钥、恢复码、Shamir、整库加密、认证式备份、检查点。

### 3.2 本期不做

- 多租户、成员体系、计费（本期单工作区；保留 `workspaces` 表与 workspace 抽象，多租户时扩展 `workspace_id` 列）。
- 云同步、托管触发服务（除非后续单独立项）。
- 移动端、小程序、浏览器插件。
- 把 Agent 做成 UI 自动化：不模拟鼠标/键盘、不点 DOM。
- 为 Agent 单独写一套后端或一套业务规则。
- 重写加密算法；只做模块迁移与接口收敛。
- 自动发布未经人工批准的政策变更。
- 遥测、埋点、远程崩溃上报。

## 5. 建设策略

### 5.1 新壳、新 IA、新契约；内核按模块迁入

- **废弃**：旧路由、旧页面结构、旧导航、旧 `dispatch.rs` 字符串路由、旧 mock 手写实现、旧 i18n 单文件、旧 CSS 双层、旧 `invoke` 直调。
- **新主壳**：Web 控制台（平台客户端）；桌面壳只负责窗口/托盘/更新，不承载业务逻辑。
- **迁入**：`crypto.rs` / `vault.rs` / `recovery.rs` / `heir_recovery.rs` / `backup.rs` 的算法与测试；`db` 的 schema 语义与迁移数据；`report/action_guide/faq` 的渲染逻辑（改造成统一文档外壳）。
- **不重写**：AES-256-GCM、Argon2id、HKDF 域分离、Shamir、SQLCipher、DPAPI。重写这些没有收益，只有风险。

### 5.2 平台核心 + 多客户端，不做微服务

平台不需要按微服务拆分。采用**一个平台核心 + 多层客户端**：

```text
web/            Web 控制台（主客户端）
apps/cli        命令行
apps/server     Platform API（REST + SSE）
apps/mcp        MCP stdio（只读/草稿工具）
        │
        ▼
core/          平台核心（模块化单体）
  foundation/  生命周期、路径、命令总线、错误、诊断
  security/    加密、保险库、密钥托管、恢复、备份
  store/       连接、schema、迁移、仓储
  domains/     资产、政策、规划、触发、交付、审核、演练
  integrations/连接注册、LLM、政策同步、邮件、心跳
  agent/       Agent Runtime、Tool Registry、Approval、Run Log
  render/      文档外壳、报告、清单、法律、FAQ
  contracts/   命令 DTO、错误码、OpenAPI、tool manifest
        │
        ▼
web/           Vue 3 平台控制台（5 主入口 + 设置工具区）
content/       政策/法律/i18n 单一事实源
contracts/     命令/错误/OpenAPI/工具单一事实源
```

**依赖规则（编译期约束）：**

1. `web` 只能通过 Platform API 访问核心，不碰文件系统、不碰 SQLite、不直调 Tauri `invoke`。
2. `agent` 只能通过 Tool Registry / CommandBus 行动，不得直连 `domains` 或 `store`。
3. `domains` 只能依赖 `store` / `security` / `contracts`，不得互相直接调用；跨域协作走应用服务。
4. `render` 是纯函数：输入 DTO，输出 HTML/文本，不读库、不写文件。
5. `integrations` 不反向依赖 `domains`；通过端口接口注入。
6. `apps/*` 不含业务逻辑，只做参数适配与生命周期；桌面壳不另写页面。

### 5.3 一个事实一个来源

| 事实 | 唯一来源 | 派生 |
|---|---|---|
| 命令名/入参/权限 | `contracts/commands.json` | IPC 注册、dispatch、CLI、HTTP、MCP、mock、tool manifest、文档 |
| 错误码/HTTP 状态/文案键 | `contracts/errors.json` | Rust 错误、前端提示、CLI 退出码 |
| 资源路由/请求响应 | `contracts/openapi.json` | TS 客户端、HTTP 路由、SDK、契约测试 |
| Agent 工具 | `contracts/tools.json` | Tool Registry、审批策略、工具目录 UI、MCP |
| 平台政策 | `content/platforms/*.json` | Rust 常量、审核候选、文档 |
| 法律模板 | `content/legal/*.json` | 前端预览、Rust 渲染、导出 |
| UI 文案 | `content/i18n/{zh-CN,en-US}/*.json` | 前端运行时、Rust 文档渲染 |
| 定位文案 | `docs/POSITIONING.md` | README、站点、应用内引导 |
| 设计令牌 | `web/src/design/tokens.css` | 全部组件与页面 |

### 5.4 工程治理与性能纪律

1. **性能预算前置。** 每个里程碑有基准数据与回归门禁；不做事后“优化一下”。
2. **加载先骨架后数据。** 首屏只等最小数据；长任务异步化；不允许全页阻塞。
3. **模块边界自动测试。** 循环依赖、禁止 import、跨域 repo、手写 URL 由 CI 阻断，不靠自觉。
4. **不可逆决策留 ADR。** schema、加密、契约、依赖、部署形态变更必须有决策记录。
5. **高级项目管理。** WIP 限制、15% 缓冲、关键路径、双轴燃尽、停止规则；缺口不允许静默延期。

## 7. 关键取舍（写死在计划里）

1. **先底座后界面。** 没有契约与数据底座就写页面，必然返工。
2. **先政策 Top 30，再谈 152。** 152 条全部核实不现实；先把高价值平台做对。
3. **不做旧路由兼容。** 旧链接一律 404；新应用只认新路径。
4. **不做“即将上线”占位。** 未完成的功能不上导航、不进安装包；只在缺口台账里。
5. **不做无测试的模块。** 每个模块必须有单元 + 契约 + 至少一条用户路径 E2E。
6. **不做无来源的政策。** 没有来源就写“未核实”，不允许编造。
7. **Agent 是一等公民。** 独立工作台、工具目录、审批队列、运行记录；不是侧边聊天装饰。
8. **前端不承载业务逻辑。** 每个动作一个命令，页面只做编排；Agent 与页面走同一后端。
9. **设置是全局工具。** 不占业务导航；避免把“配置”当成用户旅程的一站。
