# DigiLegacy 对标与定位研究报告

> 数据抓取日期：2026-10-29。stars / license / 最近推送时间均来自 GitHub REST API v3 实时响应，逐条可复核；未能取到的条目明确标注「未核实」，不编造。

## 一、结论先行

1. **赛道里没有第二个项目同时覆盖「发现→登记→规划→文档→触发→执行」六段。** 开源侧最强的是「密码库 + 紧急访问」（Bitwarden/Vaultwarden/KeePassXC），它们把受托人接管做成了生产级；但多平台政策库、法律文书、继承人引导三块，开源项目几乎全空。DigiLegacy 的六段闭环是真差异，不是话术。
2. **真正的对手不是密码库，而是「死人开关」这一支。** Aeterna（306★）、LastSignal（759★）、deadcheck（335★）都是自托管服务，只做「到期发信」一段，但它们的**触发可靠性**比单机桌面应用强一个量级——因为它们有常驻服务器。
3. **DigiLegacy 最致命的结构性缺口已经补上：** 单机应用原本只有「持有者本机解锁」一条解密路径，持有者失能后家人拿到数据库也打不开。Shamir 门限恢复包（本次实现）是目前开源同类中少见的解法，且不需要服务器。
4. **下一个真缺口是「恢复演练」**：份额生成了但没人验证过它真的能用。这一条不补，Shamir 只是心理安慰。
5. **不要拿加密算法当卖点。** AES-256-GCM + Argon2id 是全行业基线；152 平台数量也容易被复制。真正难复制的是**政策数据的持续维护**与**继承人侧的可用性工程**。

### 2.1 Bitwarden（Emergency Access 的行业标准）

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/bitwarden/clients |
| 许可证 | NOASSERTION（多许可混合：GPL-3.0 + Bitwarden License，逐目录不同） |
| Stars | 14,092（2026-10-29） |
| 语言 | TypeScript |
| 最近推送 | 2026-10-29 |

**六段覆盖**：发现 ○｜登记 ●｜规划 ◐｜文档 ◐｜触发 ●｜执行 ●

**可验证机制**
- Emergency Access 是**服务端中介的密钥再封装**，不是 Shamir：受托人接受邀请后，服务端保存一份用受托人公钥封装的 vault key；所有者失联且等待期结束后，受托人才能取回。
- 等待期 `waitTimeDays` 可配置（0–90 天），状态机含 Invited → Accepted → Confirmed → RecoveryInitiated → Approved/Rejected。**关键点：倒计时在服务端推进**，不依赖所有者设备开机。
- 密钥层级：Master Password → Argon2id/PBKDF2 → Master Key → HKDF 展开 → Symmetric Key（AES-256-CBC + HMAC）→ Item Key。注意它用 **CBC+HMAC 而非 GCM**，与 DigiLegacy 算法不兼容，不能假定额度互通。

**相对单机 Tauri 的结构性优势**：触发与等待期由常驻服务端保证；跨设备同步；合规审计（SOC2/渗透测试）。

**可采纳**：等待期三段式 + 所有者否决窗口的设计；`x25519-dalek` 做公钥封装作为 Shamir 的补充路径（支持「指定某一位继承人单独可取」）。

### 2.3 KeePassXC（离线容器的黄金标准）

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/keepassxreboot/keepassxc |
| 许可证 | NOASSERTION（GPL-2.0/GPL-3.0 混合） |
| Stars | 29,586（2026-10-29） |
| 语言 | C++ |
| 最近推送 | 2026-10-28 |

**六段覆盖**：发现 ○｜登记 ◐｜规划 ○｜文档 ◐｜触发 ○｜执行 ◐

**可验证机制**
- KDBX 4 **复合主密钥**：密码派生密钥 + 密钥文件内容 + YubiKey HMAC-SHA1 响应，三者拼接后再 SHA-256 得到 256-bit 主密钥。支持单因子、双因子、三因子任意组合。
- **参数自描述**：Argon2 的 m/t/p 参数写在 KDBX header 的 VariantDictionary 里，文件自带解密参数——换机器、换版本都能打开。这是 DigiLegacy v3 盐串设计（`v3.<m>.<t>.<p>.`）的同源思路，方向正确。
- 头部完整性用 HMAC-SHA256 块流，防篡改。

**相对单机的优势**：KDBX 是真正的「自包含加密容器」，可脱离应用长期保存（20 年后仍能解）。DigiLegacy 的备份是 JSON + 应用内解密，**脱离应用不可读**。

**可采纳**：`keepass` crate 可直接读写 KDBX 4 —— 作为「超长期归档格式」的导出选项（比自有 JSON 更抗时间）。这是明确的「不重复造轮子」机会。

### 2.4 Standard Notes（密钥层级范本）

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/standardnotes/app |
| 许可证 | AGPL-3.0 |
| Stars | 6,686（2026-10-29） |
| 语言 | TypeScript |
| 最近推送 | 2026-10-28 |

**六段覆盖**：发现 ○｜登记 ◐｜规划 ○｜文档 ●｜触发 ○｜执行 ◐

**可验证机制**
- 两级密钥：**root key → item key**。root key 由密码经 Argon2 派生，每个条目独立 item key，item key 再由 root key 封装；共享 vault 用 shared vault key 再包一层。
- 关键收益：**改密码只重封装 root→item 那一层，不需要重加密全部内容**。这对本地应用是决定性的性能优势。

**可采纳**：DigiLegacy 现在是「主密码派生密钥直接加密每个字段」，改密码必须全库重加密（实测 202 个测试中的 `test_change_password_and_backup_roundtrip` 就在跑这条路径，资产多时是 O(n) 次 AES）。改成两层密钥后，改密码只需重封装一次 master key。

**这是本次审计发现的最高性价比架构改进**（见第四节 P1-1）。

### 2.7 Aeterna（最直接的竞品：死人开关）

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/alpyxn/aeterna |
| 许可证 | GPL-3.0 |
| Stars | 306（2026-10-29） |
| 语言 | Go + React |
| 最近 release | v1.5.5（2026-09-06） |

**六段覆盖**：发现 ○｜登记 ◐｜规划 ○｜文档 ◐｜触发 ●｜执行 ◐

**可验证机制（读源码得到，非 README）**
- `backend/internal/worker/worker.go`：`time.NewTicker(1 * time.Minute)`，每轮依次跑 `checkFarewellDerivatives` → `checkReminders` → `checkHeartbeats` → `checkFarewellLetters`。**触发是每分钟轮询**，靠常驻服务保证。
- `backend/docs/sqlite-db-encryption.md`：**整库加密**（SQLCipher），且**不复用主密钥**——用 master key + 持久化 KDF context 经 **HKDF-SHA256** 派生独立 DB key，做密钥域分离。这是比 DigiLegacy 更严谨的一层（DigiLegacy 只做字段级加密，元数据与结构仍明文可读）。
- `frontend/src/lib/crypto.js`：浏览器端用 WebCrypto AES-GCM-256，IV 12 字节随机，密文 = IV‖ciphertext。**密钥以 JWK 形式在前端生成与导出**——这一点安全性弱于 DigiLegacy（前端持有明文密钥材料）。

**相对 DigiLegacy 的优势**：常驻服务 → 触发不依赖用户设备；整库加密 → 无元数据泄露。
**相对 DigiLegacy 的劣势**：需要 Docker 自托管（普通家庭用户做不到）；无多平台政策库、无法律模板、无继承人分平台指引；密钥在前端 JS 里流转。

**可采纳**：**HKDF 密钥域分离**（`hkdf` crate）——用主密钥派生「字段加密密钥」与「备份加密密钥」两个域，避免一把钥匙到处用。这是低成本的纵深防御。

### 2.9 补充：deadcheck（335★，Apache-2.0，Go）

核心机制：**不依赖自身 uptime** —— 把最终触发委托给第三方（HealthChecks.io、PagerDuty）。自己的服务挂了也不影响告警。

## 四、B. 能力缺口（按投入产出排序）

### P0-1 恢复演练（缺，必须补）
**现状**：Shamir 份额已生成，但没有任何机制验证「这 5 张纸真的能恢复」。
**风险**：用户以为已保护，实际份额抄错、打印机丢页、口令记错——失能时才发现，不可挽回。
**实现**：`run_recovery_drill()` 命令——用**测试密钥**（非真实主密钥）走完整的「拆分→编码→解码→重建→指纹校验」链路，输出每步耗时与结果；再让用户输入任意 `threshold` 份真实份额做**只读校验**（解码 + 校验和 + 指纹比对，不重建密钥、不改状态）。约 1–2 人日。
**验收**：`recovery_drill_passes_with_valid_shares` + `recovery_drill_rejects_mixed_batches`。

### P0-2 触发可靠性：入站签到（缺，强烈建议）
**现状**：用户必须打开应用点「我还安好」。老年用户不会做，等于触发链空转。
**实现**：可选 IMAP 轮询（`imap` crate），「回复任意邮件 = 签到」。默认关闭，凭据走 vault 加密。
**成本**：3–4 人日；风险：IMAP 服务器差异、OAuth2（Gmail 需要）。

### P1-1 两层密钥（root key → field key）（缺，性价比最高）
**现状**：改密码 = 全库逐字段 AES 重加密。资产 1000 条时是 6000 次 AES + 6000 次 UPDATE。
**实现**：随机生成 data key，用主密码派生 key 封装 data key；字段用 data key 加密。改密码只重封装 1 次。
**成本**：3–4 人日 + 迁移脚本（存量数据需一次性转成新结构，但可惰性迁移：读时发现旧格式则用旧路径解，写时升级）。
**收益**：改密码 O(n) → O(1)；同时为「多设备共享」留出接口。

### P1-2 密钥域分离（HKDF）
**实现**：`hkdf` crate，用主密钥派生 `field_key` / `backup_key` / `kit_key` 三个域。约 0.5 人日。
**收益**：备份泄露不等于字段密钥泄露；恢复包口令破解不等于主密钥破解。

### P2-1 整库加密（SQLCipher）——已实测，本机不可行，列 CI 路径
**现状**：字段级加密，但表结构、行数、时间戳、平台 ID 全明文。取证工具能看出「此人有 37 个账户、其中 12 个是金融类」。
**实测（2026-10-30，本机 Windows）**：三种路径全部受阻——
1. `bundled-sqlcipher` + `OPENSSL_DIR=C:\msys64\ucrt64`：sqlcipher/sqlite3.c 编译时 cl.exe 拉入 MSYS 的 GCC 风格 UCRT 头，`corecrt_wstdio.h` 语法错误 100+（MSVC 与 MSYS 头不兼容）；
2. `bundled-sqlcipher-vendored-openssl`：openssl-src 需要 **native Windows perl** 跑 `Configure VC-WIN64A`，本机只有 msys perl 5.38，Configure exit 2；
3. 调整 include 顺序（VC 头在前）可解决 1，但 sqlcipher 的 crypto 层仍要求 MSYS 路径下的 `openssl/crypto.h`——两套头无法同时满足。
**可行路径**：CI（ubuntu runner 原生 perl + libssl-dev）可直接用 `bundled-sqlcipher`；Windows 需安装 Strawberry Perl 后启用 vendored-openssl。
**当前缓解**：字段级加密 + KDBX 长期归档（KDBX 自带整库 AES-256）+ Shamir 恢复包，敏感内容已全部密文；泄露面只剩行数与表结构。

### P2-2 KDBX 导出（长期归档）
**实现**：`keepass` crate，把全部资产导出为 KDBX 4 文件。20 年后用 KeePassXC 也能打开。
**成本**：1–2 人日。**这是「脱离本应用仍可读」的唯一解**，对数字遗产产品是刚需。

### P2-3 硬件密钥（YubiKey）
`yubikey` crate，HMAC-SHA1 challenge-response 作为第二因子。3 人日，受众窄但极强信任信号。

## 五、C. 定位分析

### 5.1 用户真正为什么买单

不是「加密」。加密是门槛，不是卖点。真实动因按强度：

1. **「我死后家人找不到东西」的焦虑**，且需要一份可执行的清单——不是模糊承诺。用户买的是「可交付的行动方案」。
2. **平台条款的信息不对称**：「微信能不能继承」「支付宝余额怎么取」「B 站账号会不会被回收」——这些答案散落在客服话术、判例、部门规章里。**把散落信息整理成可执行步骤，是这个产品最硬的价值。**
3. **一次性买断**：订阅制与「死后才用」的产品天然冲突。
4. **不信任云端**：把全部账号密码交给一家创业公司，风险高于自己保管。

### 5.2 为什么「本地化 / i18n」不是差异化

- 多语言 UI 是两周工程，任何团队都能做。
- 真正的本地化壁垒是**司法辖区的法律实质差异**：中国大陆的继承公证流程、台湾的限定继承、香港的遗产承办书、美国的 probate——法律文书模板与平台政策必须逐辖区重写。
- 把「支持中英文」当卖点，等价于把「有设置页」当卖点。**README 里现在没有这么写，这是对的；不要加回去。**

### 5.3 真正的壁垒（按难复制程度排序）

| 壁垒 | 为什么难复制 | DigiLegacy 现状 |
|---|---|---|
| **政策数据的持续维护** | 152 个平台的政策页会变；维护是线性人力，无法一次性完成 | 有 152 条，但仅 5 条有 `data_source`，147 条「未核实」——**这是最大的诚实性缺口，也是最大的机会** |
| **继承人侧的可用性** | 产品价值在「家人真的拿到」那一刻兑现；需要纸质件、离线工具、分步指引 | 有 HTML 报告 + 工具包 + 恢复包；**缺恢复演练** |
| **触发可靠性** | 单机应用在用户失能时无法自证；需要外部见证或多通道冗余 | 三级 DMS + SMTP + 可选心跳；**缺入站签到** |
| **密码学托管** | 无服务器 = 丢恢复码就永久丢数据；需要精心设计恢复路径 | Argon2id + 24 位恢复码 + Shamir 3-of-5，**已补齐** |
| **法律合规** | 逐辖区法律顾问网络 | 有模板，无辖区参数化 |

### 5.4 宣称逐条去伪

| 宣称 | 判定 | 依据 |
|---|---|---|
| 六段链路闭环 | **真优势** | 矩阵中唯一六段全 ● 的项目；其余项目最多 3 段 |
| 152 平台政策库 | **半真** | 数量是优势，但 147/152 未核实来源；**数量易复制，维护难复制** |
| AES-256-GCM 字段级加密 | **基线，非卖点** | 全行业标准；且字段级不等于整库加密（元数据仍泄露） |
| 三级确认链 | **真优势（有条件）** | 三级等待 + 可撤销优于单级；但依赖 SMTP 单通道 |
| 无服务器 / 无遥测 | **真优势（有代价）** | 隐私承诺真实；代价是触发可靠性与恢复可用性，需 Shamir + 演练补偿 |
| Shamir 3-of-5 恢复包 | **真优势（新）** | 开源同类中少见；`sharks` crate 正确性可用测试验证 |
| Argon2id | **基线，非卖点** | 相对 PBKDF2 是必要升级，但属行业标准 |

## 六、给 DigiLegacy 的三条结论

1. **继续守住「六段闭环 + 单机无服务器」这个组合**——这是矩阵里唯一没人占的位置，且真实存在需求（不信任云端的家庭用户）。
2. **把「政策库可溯源」做成产品能力而不是合规负担**：每条政策显示「来源 / 最后核对时间 / 置信度」，让用户自己判断。147 条未核实不是耻辱，隐藏它才是。这一点已经写进代码（`UNVERIFIED_SOURCE` 常量 + 棘轮测试），方向正确。
3. **补齐「恢复演练」与「入站签到」**——前者决定 Shamir 是不是心理安慰，后者决定触发链是不是空转。这两条补完，产品承诺才真正闭环。
