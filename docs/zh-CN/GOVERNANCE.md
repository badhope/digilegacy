# 工程治理

[English](../GOVERNANCE.md) | 简体中文

项目要跑得快，也要守得住边界。下面这些规则让变更可预期，而不是靠默契。

## 原则

1. 先写清用户结果、接口和验收标准，再开始实现。
2. 保持一个事实源：命令、错误和 schema 只在 `contracts/`。
3. 入口层不持有业务逻辑。
4. 不可逆变更必须留下决策记录。
5. 不伪造完成；不支持的路径要明确失败。

## 角色

| 角色 | 职责 |
|---|---|
| 产品负责人 | 用户结果、优先级与验收口径 |
| 架构负责人 | 契约、模块边界、ADR 与跨域决策 |
| 模块负责人 | 领域实现、测试、迁移与回滚 |
| 前端负责人 | 入口、加载、可访问性与设计系统 |
| 安全与数据负责人 | Vault、密钥、备份、迁移与审计 |
| Reviewer | 独立审查契约、权限、数据影响与测试 |

一个人可以承担多个角色；同一个 Agent 不能批准自己的改动。

## 进入开发前

- 用户结果具体，不是“优化一下”。
- 明确所属模块和负责人。
- 列出涉及的命令、工具与 schema。
- 写明权限档位。
- 说清数据影响：表、字段、迁移和回滚。
- 验收覆盖命令、页面状态、错误与性能。
- 外部依赖和风险已登记。
- 不可逆变更已有 ADR 或 RFC 草稿。

## 完成标准

- 业务逻辑在领域层或应用层，不在入口层。
- 错误使用契约错误码。
- 写操作有权限、审批和审计边界。
- 新行为有单元或集成测试。
- 页面覆盖加载、空态和错误态。
- 生成物已同步。
- 架构门禁通过。
- 文档与更新日志已更新。
- 没有密钥或敏感值进入工作树。
- `./tools/verify.sh` 通过。

## 变更分级

| 级别 | 例子 | 要求 |
|---|---|---|
| 局部 | 文案、样式、单页交互 | Pull Request + 自测 |
| 契约 | 新命令、工具或 schema | 设计说明、生成器、消费者检查 |
| 数据 | 迁移或字段语义 | 变更单、备份与回滚方案、二次复核 |
| 安全 | 加密、密钥、恢复、权限 | ADR、安全评审与测试向量 |
| 发布 | 版本、签名、合规 | 发布检查单与回滚演练 |

## ADR 与 RFC

ADR 记录已经做出、难以回退的决定；RFC 讨论还没定的方案。两者分别放在 `docs/adr/` 和 `docs/rfc/`。ADR 要写背景、决定、替代方案、后果和复审条件。

## 评审重点

Reviewer 优先看：是否出现第二事实源、是否绕过权限、Agent 是否能自批、数据是否会丢、失败是否被伪装成成功、移动端是否溢出、页面是否被整页阻塞、性能是否回退。测试全绿不能成为破坏边界的理由。

## 节奏

每次改动跑快速门禁，合并前跑完整门禁，用户会碰到的路径做手动 smoke。定期看性能预算和未决风险。里程碑不是因为代码写完就算完成，而是验收路径跑通、剩余缺口写清楚。
