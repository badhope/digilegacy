# 架构说明

[English](../ARCHITECTURE.md) | 简体中文

DigiLegacy 是带多个入口、共用同一个命令层的模块化单体。设计优先明确边界，不提前拆微服务。

## 总体形态

```text
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ Web 控制台   │ CLI          │ MCP 服务     │ HTTP 客户端  │
└──────┬───────┴──────┬───────┴──────┬───────┴──────┬───────┘
       │              │              │              │
       └──────────────┴──────┬───────┴──────────────┘
                             │
                    平台 API / CommandBus
                             │
                 ┌───────────┴───────────┐
                 │        应用层         │
                 └───────────┬───────────┘
                             │
        ┌──────────┬─────────┼─────────┬──────────┐
        │ 领域层   │ 安全    │ 存储    │ 外部集成 │
        └──────────┴─────────┴─────────┴──────────┘
                             │
                   审计 · 任务 · 审批
```

入口层只负责传输、鉴权和展示，不持有业务规则。统一分发器把命令交给应用服务，应用服务再调用领域模块和基础设施。

## 契约先行

命令、工具、错误码和输入/输出 schema 都声明在 `contracts/`。生成器负责产出 Rust 命令表与错误表、HTTP 路由与 OpenAPI、CLI 元数据、MCP 工具目录，以及 Web 的类型、IPC 和 mock 数据。

生成文件不手改。`node tools/generate.mjs --check` 是发布门禁的一部分；接口改了但没有同步到所有客户端，合入前就会失败。

每条命令声明权限档位：`read`、`draft`、`write`、`key`、`network`、`desktop`。HTTP 开放读与草稿，写操作要求 Bearer token，后三档永远拒绝。MCP 只暴露读与草稿。

## 应用层与领域层

`core/application` 负责编排用例：读取状态、校验输入、调用领域函数、持久化并追加审计。只有这一层知道一次用户操作由哪些步骤组成。

`core/domains` 保存与入口无关、必须始终成立的规则：资产归属、继承人关系、触发状态迁移、政策来源、同步候选和审批语义。领域代码不关心 HTTP、Vue 或 CLI 参数。

`core/integrations` 是外部系统的边界：HTTP feed、SMTP、LLM、Webhook 与连接探针。网络访问隔离在这里，返回结构化结果，不把传输错误泄漏进领域层。

出站 URL 在建立连接前统一校验：只允许 HTTP/HTTPS，不允许内嵌账号信息或控制字符，并拒绝云元数据、链路本地和私网字面地址。回环地址保留给本地测试；局域网端点需要显式设置 `DIGILEGACY_ALLOW_PRIVATE_NETWORK=1`。政策同步在拉取远端 feed 前也会走同一道校验。

## 数据与安全

SQLCipher 保护落盘数据库，敏感字段在写入前还会再做一次字段级加密。密钥只在进程内存中派生和使用，不进入日志、导出报告或浏览器存储。

Vault 支持恢复码、Shamir 分片、认证备份和检查点。破坏性操作必须显式确认并产生审计事件。审计记录组成哈希链，后续篡改可以被发现。

## Agent 模型

一次 Agent 运行是一条持久化状态机：

1. 规划器用已注册工具提出步骤。
2. 只读步骤立即执行。
3. 写步骤创建审批并暂停运行。
4. 人批准或拒绝，并写下理由。
5. 运行恢复、完成或停止；每次状态迁移都有记录。

审批是一等记录，不是前端开关。后台 Worker 恢复已批准的运行并回收失联任务。Agent 不能批准自己的请求，也接触不到密钥、网络和桌面命令。

## 存储与迁移

schema 变更在 `core/store/src/schema.sql` 中按版本管理，通过迁移账本应用。每次迁移都有名称、版本和测试：打开旧库、升级、验证结果。运行诊断只暴露当前 schema 版本和表数量，不暴露数据。

## 前端

Web 控制台是 Vue 3 应用，包含五个业务区和全局设置。路由懒加载，数据访问统一走类型化平台客户端。读取有短 TTL 缓存和并发去重；写成功后按域失效，保证下一页拿到新数据。桌面与移动端、亮色与暗色主题都纳入验收。

## 可观测与运维

服务端提供健康检查、结构化命令信封、trace ID 和审计查询。后台任务有明确状态与错误码。连接探针报告健康状态但不返回凭据。诊断包可以生成支持材料，并排除密钥。

## 部署

部署需要 Rust 服务、一个可写数据目录和 API token。Web 控制台可以放在任意静态服务器，指向平台 API。CLI 与 MCP 在本地运行，连同一个数据库或 API。SQLite/SQLCipher 让默认部署保持轻量；以后需要共享服务时，命令层可以整体上移，客户端不用改。

## 不做的事

- 为拆微服务而拆微服务。
- 给 Agent 单独写一套后端。
- 手改生成客户端。
- 用乐观 UI 掩盖失败。
- 把本地部署当成另一套产品。

更多取舍见[架构决策](adr/)。
